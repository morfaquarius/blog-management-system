## О проекте

Blog Management System — учебная основа для создания REST API блога. Проект предназначен для практики:

- построения HTTP API и работы с JSON;
- разделения приложения на handler, service и repository;
- регистрации пользователей и авторизации;
- хеширования паролей и использования JWT;
- работы с PostgreSQL и SQL-миграциями;
- валидации входных данных и обработки ошибок;
- middleware для аутентификации, логирования и восстановления после паник;
- асинхронного логирования событий.

## Состояние проекта

В репозитории уже есть модели пользователей, постов и комментариев, интерфейсы сервисов и репозиториев, SQL-файлы миграций, пример окружения и конфигурация PostgreSQL в Docker Compose.

До запуска полноценного сервиса еще предстоит завершить:

- `api/main.go`: конфигурацию, подключение к базе, сборку зависимостей, роутер и HTTP-сервер;
- `pkg/database`: открытие соединения и выполнение миграций;
- `internal/repository` и `internal/service`: операции с данными и бизнес-логику;
- `internal/handler` и `internal/middleware`: обработчики и middleware;
- `pkg/auth`: реализацию JWT и хеширования паролей;
- `internal/logger`: запись событий;
- Docker-сборку: текущий `Dockerfile` указывает на `cmd/api/main.go`, которого в структуре проекта нет.

Сервис приложения в `docker-compose.yml` пока закомментирован — Compose запускает только PostgreSQL. Команда `go run ./api` пока не поднимает готовый API-сервер.

## База данных

`docker-compose.yml` создает базу `blog_db` с пользователем `postgres`. SQL-миграции находятся в каталоге `migrations/`:

1. `001_init_schema.sql` — таблицы `users`, `posts` и `comments`;
2. `002_add_foreign_keys.sql` — связи между пользователями, постами и комментариями;
3. `003_create_indexes.sql` — индексы для часто используемых запросов.

Таблица пользователей хранит имя, email и хеш пароля. Пост связан с автором, комментарий — с постом и автором. Схема задает каскадное удаление связанных записей.

Функция `Migrate` в `pkg/database/migrate.go` пока не реализована, поэтому наличие SQL-файлов само по себе не применяет миграции.

Полезные команды для базы:

```bash
# Запустить PostgreSQL
docker compose up -d db

# Проверить состояние контейнеров
docker compose ps

# Остановить контейнеры, сохранив volume базы
docker compose down
```

Для удаления локальных данных базы вместе с контейнерами используйте `docker compose down -v`; эта команда удалит volume PostgreSQL.

## Планируемый API

Маршруты ниже следуют TODO-комментариям в `api/main.go` и обработчиках. Они описывают предполагаемый контракт, но пока не зарегистрированы в работающем сервере.

### Публичные маршруты

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | Проверка состояния API |
| `POST` | `/api/register` | Регистрация пользователя |
| `POST` | `/api/login` | Вход пользователя |
| `GET` | `/api/posts` | Список постов с пагинацией |
| `GET` | `/api/posts/{id}` | Получение поста |
| `GET` | `/api/posts/author/{authorID}` | Посты автора с пагинацией |
| `GET` | `/api/posts/{postId}/comments` | Комментарии поста с пагинацией |

### Защищенные маршруты

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/posts` | Создание поста от имени текущего пользователя |
| `POST` | `/api/posts/{postId}/comments` | Добавление комментария от имени текущего пользователя |

Для защищенных запросов целевой формат заголовка:

```http
Authorization: Bearer <token>
```

Сервисы предполагают пагинацию через параметры `limit` и `offset`. Для списка постов в комментариях к обработчику указан `limit` по умолчанию `10` с диапазоном от `1` до `100`; конкретное поведение остальных endpoint следует согласовать при реализации.

## Примеры запросов

Примеры ниже иллюстрируют предполагаемый API-контракт. Они начнут работать после реализации маршрутов, обработчиков, сервисов и запуска сервера.

### Проверка состояния

```bash
curl http://localhost:8080/api/health
```

### Регистрация пользователя

Запрос соответствует полям `UserCreateRequest`: `username`, `email`, `password`.

```bash
curl -X POST http://localhost:8080/api/register \
  -H "Content-Type: application/json" \
  -d '{
    "username": "testuser",
    "email": "test@example.com",
    "password": "password123"
  }'
```

Предполагаемая структура успешного ответа задана типом `TokenResponse`:

```json
{
  "token": "<jwt>",
  "expires_at": "2026-11-25T18:00:00Z",
  "user": {
    "id": 1,
    "username": "testuser",
    "email": "test@example.com",
    "created_at": "2026-11-25T17:00:00Z"
  }
}
```

### Вход пользователя

```bash
curl -X POST http://localhost:8080/api/login \
  -H "Content-Type: application/json" \
  -d '{
    "email": "test@example.com",
    "password": "password123"
  }'
```

### Создание поста

```bash
curl -X POST http://localhost:8080/api/posts \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <jwt>" \
  -d '{
    "title": "Мой первый пост",
    "content": "Текст публикации"
  }'
```

### Получение постов

```bash
# Список с пагинацией
curl "http://localhost:8080/api/posts?limit=10&offset=0"

# Один пост
curl http://localhost:8080/api/posts/1

# Публикации автора
curl "http://localhost:8080/api/posts/author/1?limit=10&offset=0"
```

### Комментарии

```bash
# Добавить комментарий
curl -X POST http://localhost:8080/api/posts/1/comments \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <jwt>" \
  -d '{
    "content": "Спасибо за публикацию!"
  }'

# Получить комментарии
curl "http://localhost:8080/api/posts/1/comments?limit=10&offset=0"
```

### Формы данных

Модели в `internal/model/models.go` задают поля запросов и ответов. Например, запрос на публикацию содержит `title` и `content`, а ответная модель поста также включает автора:

```json
{
  "id": 1,
  "title": "Мой первый пост",
  "content": "Текст публикации",
  "author": {
    "id": 1,
    "username": "testuser",
    "email": "test@example.com",
    "created_at": "2026-11-25T17:00:00Z"
  },
  "created_at": "2026-11-25T17:10:00Z"
}
```

Для входных данных предусмотрены validation-теги:

- имя пользователя: от 3 до 50 символов;
- email: должен иметь корректный формат;
- пароль при регистрации: не менее 6 символов;
- заголовок поста: от 1 до 200 символов;
- текст комментария: от 1 до 1000 символов;
- идентификатор поста в запросе комментария: положительное число.

## Архитектура

Поток обработки запроса, на который ориентирована структура проекта:

```text
HTTP request
     │
     ▼
Middleware (auth, logging, recovery, CORS)
     │
     ▼
Handler (HTTP, JSON, status codes)
     │
     ▼
Service (business rules)
     │
     ▼
Repository (SQL queries)
     │
     ▼
PostgreSQL
```

- **Handler** принимает HTTP-запрос, разбирает входные данные и формирует ответ.
- **Service** выполняет бизнес-операции и возвращает ошибки предметной области.
- **Repository** инкапсулирует запросы к PostgreSQL.
- **Model** описывает сущности и структуры запросов/ответов; пароль пользователя исключен из JSON-представления.
- **Middleware** должен обрабатывать аутентификацию и общие аспекты HTTP-запросов.
- **Event logger** задуман для асинхронной записи событий создания публикаций и комментариев.

## План реализации по компонентам

Этот раздел помогает ориентироваться в `TODO` и описывает назначение файлов, а не утверждает, что функции уже работают.

### Подключение к PostgreSQL и миграции

В `pkg/database/init.go` предполагаются функции для создания DSN, открытия и проверки соединения, настройки пула и закрытия БД. В `pkg/database/migrate.go` нужно прочитать SQL-файлы из `migrations/`, отсортировать их по имени и выполнить последовательно.

### Репозитории

Интерфейсы находятся в `internal/repository/interfaces.go`, реализации разделены по файлам:

- `user_repo.go` — создание и поиск пользователя, проверка email и имени;
- `post_repo.go` — создание, поиск, списки и подсчет публикаций;
- `comment_repo.go` — создание и выборка комментариев к посту.

Методы репозиториев должны принимать `context.Context` и возвращать ошибки вызывающему слою.

### Сервисы

- `user_service.go` — валидация регистрации, проверка уникальности учетных данных, хеширование пароля, вход и выпуск JWT;
- `post_service.go` — создание публикации, получение постов и пагинация;
- `comment_service.go` — создание комментария и получение комментариев поста.

Сервисы отделяют правила приложения от HTTP и SQL. HTTP-коды следует формировать в обработчиках, а сервисам возвращать ошибки приложения.

### Обработчики и ошибки

Обработчики в `internal/handler/` должны разбирать JSON, валидировать запросы, вызывать сервисы и кодировать ответы. В `handler/utils.go` предусмотрены общие функции формирования ошибки и преобразования ошибок сервиса в HTTP-статусы.

В TODO для `HandleServiceError` заданы основные соответствия:

| Ошибка | HTTP-статус |
|---|---:|
| Пользователь уже существует | `409 Conflict` |
| Неверные учетные данные | `401 Unauthorized` |
| Пост или комментарий не найден | `404 Not Found` |
| Доступ запрещен | `403 Forbidden` |
| Ошибка валидации | `400 Bad Request` |
| Неизвестная ошибка | `500 Internal Server Error` |

### Аутентификация и middleware

`pkg/auth/jwt.go` содержит типы для JWT claims и менеджера токенов. `pkg/auth/password.go` задает функции для bcrypt. После реализации `AuthMiddleware` должен извлекать bearer-токен из `Authorization`, проверять его и передавать ID пользователя через request context.

В `internal/middleware/logging.go` также предусмотрены middleware для логирования запроса, обработки паник и CORS. Сейчас эти методы содержат `TODO`.

### Event logger

`internal/logger/event_logger.go` задуман для асинхронного логирования событий создания постов и комментариев: обработчики отправляют событие в канал, worker записывает его в файл. Сам журнал и его жизненный цикл нужно реализовать; путь к файлу и формат событий в текущей конфигурации не заданы.

## Пошаговое руководство

Удобнее всего делать проект небольшими «вертикальными срезами»: реализовать один небольшой кусок от базы до HTTP, проверить его, затем переходить к следующему. Не начинайте с написания всех обработчиков сразу: без работающих зависимых слоев трудно определить, где возникла ошибка.

### Шаг 1. Установите исходное состояние

Из корня репозитория выполните:

```bash
go version
go mod download
docker compose up -d db
docker compose ps
```

Убедитесь, что версия Go совместима с `go.mod`, а контейнер `db` перешел в состояние `healthy`. Если локальный порт `5432` уже занят, измените левую часть `5432:5432` в Compose и `DB_PORT` в `.env`. Не меняйте порт контейнера справа.

До внесения изменений полезно выполнить `go test ./...` и сохранить вывод: в стартовом каркасе команда может завершиться ошибкой из-за неготовых функций или импортов. Это не повод игнорировать новые ошибки. По мере работы добивайтесь, чтобы затронутый пакет собирался и его тесты проходили.

### Шаг 2. Создайте схему базы

Проверьте последовательность миграций:

1. создать таблицы и ограничения столбцов;
2. добавить внешние ключи;
3. создать индексы для запросов.

Реализуйте `database.Migrate` так, чтобы каталог миграций определялся надежно. Не полагайтесь на текущую рабочую директорию процесса: `go run ./api`, запуск бинарного файла и контейнер могут иметь разные рабочие каталоги. Практичное решение для учебного проекта — передавать путь к каталогу миграций в конфигурацию либо искать его относительно явно известного корня приложения.

Отсортируйте миграции по имени и обрабатывайте ошибку каждого чтения и SQL-запроса с именем файла в контексте. Важно: `001_init_schema.sql` использует `IF NOT EXISTS`, но добавление ограничений в `002_add_foreign_keys.sql` не защищено от повторного запуска. Если выполнять все миграции при каждом старте, второй запуск может завершиться ошибкой. Для надежного решения заведите таблицу истории миграций и применяйте каждый файл ровно один раз; альтернативно обеспечьте идемпотентность SQL осознанно. Для более сложного варианта применяйте одну миграцию в транзакции.

Проверьте, что миграции реально применились, например подключившись к контейнеру:

```bash
docker compose exec db psql -U postgres -d blog_db
```

В `psql` можно использовать `\dt` для списка таблиц, а `\d users` — для проверки конкретной таблицы.

### Шаг 3. Реализуйте подключение к базе

В `pkg/database/init.go`:

1. Соберите DSN из `database.Config`; не печатайте его в лог, так как он содержит пароль.
2. Откройте `*sql.DB` через `sql.Open`. Этот вызов создает пул, но сам по себе не подтверждает соединение.
3. Вызовите `Ping`/`PingContext`, чтобы проверить доступность PostgreSQL.
4. Если проверка не удалась, закройте уже созданный пул и верните ошибку с причиной через `%w`.
5. Настройте пул соединений и закройте его при ошибке старта/завершении приложения.

`database/sql` безопасно переиспользует `*sql.DB` между горутинами; обычно создают один пул на приложение, а не отдельное соединение на запрос.

### Шаг 4. Завершите модели и проверку входа

В `internal/model/models.go` выполните `Validate()` через `validator.New().Struct(r)` для каждого request DTO. Добавьте тесты на валидный пример и на нарушения каждого значимого ограничения.

Проверьте важные границы: пустое значение, минимальную и максимальную длину, некорректный email, отрицательный ID. `required` у числового поля проверяет, что значение не равно нулю; для явного диапазона используйте подходящие validation-теги. В запросе комментария `PostID` существует в DTO, но целевой маршрут также несет `postId`. При `POST /api/posts/{postId}/comments` источником истины должен быть ID из URL; не позволяйте телу запроса подменить родительский пост. Можно сформировать DTO из URL и тела или изменить DTO, сохраняя один однозначный контракт.

Функция `User.ToResponse()` должна копировать только публичные поля. Никогда не сериализуйте пароль или bcrypt-хеш в ответ API.

### Шаг 5. Реализуйте репозитории по одному методу

Начните с пользователя, затем перейдите к постам и комментариям. Для каждой операции:

1. напишите SQL с параметрами (`$1`, `$2` для PostgreSQL), не вставляйте пользовательские данные через `fmt.Sprintf`;
2. передайте `context.Context` в `QueryContext`, `QueryRowContext` или `ExecContext`;
3. перечислите столбцы явно и сканируйте их в том же порядке;
4. проверьте ошибку запроса и сканирования;
5. добавьте контекст к ошибке через `fmt.Errorf("...: %w", err)`.

Для `QueryRowContext` отсутствие строки обычно приходит как `sql.ErrNoRows`. Репозиторию следует выбрать и соблюдать единый контракт. В этих заготовках комментарии предлагают `nil, nil` для отсутствующей записи, после чего сервис преобразует `nil` в `ErrUserNotFound`, `ErrPostNotFound` или другую ошибку предметной области. Не превращайте прочие ошибки базы в «не найдено».

Для `Create` используйте `INSERT ... RETURNING id` и `Scan(&model.ID)`. Для списков не забудьте `defer rows.Close()`, цикл `rows.Next()` и проверку `rows.Err()` после цикла. Пустой результат списка обычно лучше представлять пустым слайсом `[]`, а не `null`.

Уникальность username/email обеспечивается ограничением БД. Проверка `ExistsByEmail` до вставки улучшает сообщение пользователю, но не защищает от двух одновременных регистраций: окончательным источником истины остается уникальное ограничение БД. Обработайте конфликт ограничения и верните подходящую доменную ошибку.

### Шаг 6. Добавьте доменные ошибки и сервисы

Сначала определите ошибки в `internal/errors/apperrors/errors.go`. Проверяйте их через `errors.Is`, а не сравнивайте строки сообщений.

Сервис отвечает за правила предметной области, но не за HTTP:

- регистрация: проверить DTO, проверить уникальность, захешировать пароль, сохранить пользователя, создать JWT, собрать `TokenResponse`;
- вход: найти пользователя по email, сравнить пароль с хешем, не раскрывать в ответе, существует ли такой email, выпустить токен;
- создание поста: убедиться, что автор известен/аутентифицирован, валидировать запрос и сохранить пост;
- создание комментария: проверить положительный ID и существование поста, проверить текст и сохранить связь с автором;
- чтение списков: проверить пагинацию, запросить данные и общее количество.

При регистрации ошибка на любом этапе должна прекращать операцию. Не возвращайте успешный пустой ответ (`nil, nil`) из незавершенных ветвей. При добавлении нескольких связанных записей подумайте, нужна ли транзакция.

Сейчас `CommentService` хранит `*repository.CommentRepo`, тогда как интерфейс `CommentRepository` уже объявлен. Для последовательного разделения слоев лучше принимать интерфейс в поле и конструкторе. Также сверьте имена конструкторов: в исходном TODO `main.go` написаны `NewUserRepository` и `NewPostRepository`, а фактические функции называются `NewUserRepo` и `NewPostRepo`. Для комментариев конструктор принимает конкретный `*CommentRepo`. Используйте объявления в исходных файлах как источник истины и согласуйте сигнатуры перед сборкой приложения.

### Шаг 7. Реализуйте JWT и middleware аутентификации

В `pkg/auth/jwt.go`:

1. При создании менеджера преобразуйте срок жизни в `time.Duration`; проверьте, что секрет непустой, а срок положительный.
2. При генерации задайте claims пользователя и стандартные claims `IssuedAt`, `NotBefore`, `ExpiresAt`, `Issuer` и `Subject`.
3. Подписывайте только ожидаемым алгоритмом HMAC-SHA256.
4. При разборе токена проверяйте подпись, алгоритм и срок действия. Не доверяйте claims до успешной проверки подписи.
5. Различайте просроченный токен и некорректный/подписанный другим ключом токен, используя предусмотренные ошибки.

В `AuthMiddleware` извлекайте строго один bearer-токен из `Authorization`. Если заголовок отсутствует или некорректен, защищенный маршрут должен вернуть `401` и не вызывать следующий handler. После успешной проверки передавайте в новый request context ID/email/username из проверенных claims. Не передавайте в контекст значения из тела запроса.

`OptionalAuth` отличается тем, что отсутствие или некорректность токена не блокирует публичный запрос. Это не означает, что такой middleware следует устанавливать на защищенные маршруты.

### Шаг 8. Реализуйте HTTP-обработчики

Общий шаблон handler:

1. проверить HTTP-метод, если маршрутизация не гарантирует его;
2. декодировать JSON в request DTO и вернуть `400` при поврежденном JSON;
3. проверить запрос и параметры URL/query;
4. получить пользователя из контекста для защищенного действия;
5. вызвать соответствующий метод сервиса с `r.Context()`;
6. передать ошибку в единое преобразование доменных ошибок;
7. установить `Content-Type`, записать статус и JSON-ответ.

Не продолжайте обработку после записи ошибки. Записывайте статус только один раз. Для списков выберите единый формат, например объект с `items` и `total`; сами модели ответа `PostResponse` и `CommentResponse` содержат вложенного автора, поэтому handler/service должны получить данные автора. Если для этого добавляются дополнительные запросы, учитывайте N+1 запросов и по возможности используйте JOIN или пакетную загрузку.

Передавайте в защищенные методы ID из контекста middleware. Для `GET /api/posts/{id}` requestorID может быть нулевым, если метод действительно доступен без авторизации; договоритесь, что означает это значение, чтобы не смешивать «анонимного пользователя» с валидным ID.

### Шаг 9. Зарегистрируйте маршруты и соберите приложение

В `api/main.go` создайте зависимости в порядке от инфраструктуры к HTTP:

```text
конфигурация → БД → миграции → JWT → репозитории → сервисы
→ обработчики → middleware → router → HTTP server
```

При запуске обрабатывайте ошибки явно и закрывайте уже созданные ресурсы, если следующий шаг завершился ошибкой. Для сервера задайте таймауты чтения/записи/заголовков, запускайте `ListenAndServe`, ожидайте `SIGINT`/`SIGTERM`, затем вызовите `Shutdown` с ограниченным контекстом и закройте БД.

Путь `/api/posts/{id}` не должен перехватывать более специфичный `/api/posts/author/{authorID}`. В chi удобнее регистрировать их в иерархии `/api/posts` и `/api/posts/author/{authorID}`, либо убедиться в порядке и поведении маршрутов тестом. Если `RequireAuth` имеет сигнатуру `func(http.HandlerFunc) http.HandlerFunc`, используйте адаптер `ToMiddleware` при подключении к `chi.Router`, который ожидает `func(http.Handler) http.Handler`.

Проверьте, что методы API имеют правильные HTTP-коды: регистрация и создание ресурсов обычно `201`, успешное чтение/вход `200`, некорректный запрос `400`, отсутствие аутентификации `401`, недостаток прав `403`, отсутствие ресурса `404`, конфликт уникальности `409`, внутренняя ошибка `500`.

### Шаг 10. Завершите Docker-запуск

Сейчас Dockerfile компилирует `./cmd/api/main.go`, хотя точка входа расположена в `api/main.go`. После завершения приложения обновите build target, проверьте копирование миграций и используйте в контейнере тот путь, который ожидает код. Затем раскомментируйте/добавьте сервис `app` в Compose и подключите его к `db` через имя сервиса `db`, а не `localhost`.

Убедитесь, что API слушает `0.0.0.0` внутри контейнера, а Compose ожидает `service_healthy` у базы. Для production не храните секреты в compose-файле или Docker-образе.

## Ключевые концепции

### DTO и JSON

Структуры запросов и ответов отделяют внешний API-контракт от хранения данных. Поле `Password` модели `User` имеет JSON-тег `json:"-"`, поэтому его нельзя включать в JSON-ответ.

### JWT и контекст запроса

После регистрации или входа сервис должен сформировать токен, содержащий идентификатор пользователя, email и username. Защищенный обработчик получает личность пользователя из контекста, который добавляет middleware после проверки токена. Не следует принимать ID автора из тела запроса для защищенных операций — автор определяется по проверенному токену.

### Пароли

Хранить нужно только bcrypt-хеш пароля. Функции `HashPassword` и `CheckPassword` описаны в `pkg/auth/password.go`, но пока не реализованы.

### Пагинация

Списки постов и комментариев проектируются с параметрами `limit` и `offset`. Обработчики должны проверять значения до передачи в сервис и возвращать согласованный формат с данными и общим количеством записей.

### Завершение приложения

## Правила и типичные ошибки

- **Не проглатывайте ошибки.** `return nil, nil` — допустимый контракт только для явно согласованного случая «не найдено» в репозитории; в остальных случаях он маскирует дефект.
- **Не теряйте исходную ошибку.** Оборачивайте ее через `%w`, чтобы вызывающий код мог использовать `errors.Is`/`errors.As`.
- **Не строьте SQL конкатенацией.** Для значений используйте параметры PostgreSQL `$1`, `$2`; динамические имена столбцов нельзя безопасно передавать как обычные параметры.
- **Не доверяйте ID автора от клиента.** Для создания поста и комментария берите автора только из подтвержденных JWT claims.
- **Не возвращайте хеш пароля.** Даже bcrypt-хеш считается секретным и не должен попадать в JSON или обычные логи.
- **Проверяйте пагинацию.** `limit` должен быть ограничен сверху, `offset` — неотрицательным. Иначе клиент может запросить чрезмерно большой объем данных.
- **Делайте порядок результатов стабильным.** При пагинации сортируйте не только по времени, но при необходимости и по ID, чтобы записи с одинаковым timestamp не перескакивали между страницами.
- **Не запускайте миграции без учета повторного старта.** История примененных миграций предотвращает повторный `ALTER TABLE` и дает понятный контроль схемы.
- **Не используйте `localhost` между контейнерами.** Приложение обращается к PostgreSQL по hostname Compose-сервиса (`db`); `localhost` внутри контейнера означает сам контейнер приложения.
- **Следите за сигнатурами конструкторов.** Комментарии в `api/main.go` — план, но фактические функции и интерфейсы в исходных файлах могут отличаться.
- **Не объявляйте маршруты только в README.** После регистрации проверяйте их HTTP-тестами: документация описывает контракт, а не реализует его.
- **Не логируйте секреты и токены.** Не выводите пароль БД, JWT secret, пароль пользователя или полный bearer-токен.

## Тестирование

Пишите тесты одновременно с реализацией, начиная с простых функций и переходя к интеграции.

### Уровни тестов

1. **Unit-тесты моделей и auth:** проверка границ валидации, преобразования `UserResponse`, сравнения bcrypt, валидного/невалидного/просроченного JWT.
2. **Тесты сервисов:** подставьте fake/mock репозитории и проверьте успешный сценарий, отсутствие сущности, конфликт уникальности и ошибки зависимости. Интерфейсы репозиториев для этого и полезны.
3. **Тесты handler:** используйте `net/http/httptest` с fake service; проверьте статус, Content-Type, JSON, ошибочный JSON, неправильный метод и отсутствие/невалидность авторизации.
4. **Интеграционные тесты PostgreSQL:** проверяйте SQL-запросы, ограничения, миграции, пагинацию и ошибки уникальности на отдельной тестовой базе. Не запускайте тесты на пользовательской базе с ценными данными.
5. **Проверка приложения:** запустите API и проверьте полный сценарий от регистрации до создания поста и комментария.

Полезный минимальный набор проверок после изменений:

```bash
gofmt -w путь/к/измененным.go
go test ./...
go vet ./...
```

Для HTTP-тестов не требуется запускать настоящий сервер: `httptest.NewRecorder` и `httptest.NewRequest` позволяют проверить handler напрямую. Интеграционные тесты базы должны быть отделены от обычных unit-тестов (например, build tag или отдельная конфигурация), чтобы `go test ./...` не требовал секретов и работающего внешнего сервиса.
